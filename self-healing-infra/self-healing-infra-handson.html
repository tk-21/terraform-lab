# 自己修復インフラ ハンズオン

AWS Config + Lambda + Ansible で SG の設定ドリフトを自動検知・修復するシステム。

## アーキテクチャ
SG → AWS Config → Config Rule → EventBridge → Lambda (boto3) → Chatwork
Ansible: ローカルPC から手動確認・再適用（EC2 は使わない）

## 前提
- AWS CLI v2 設定済み（ap-northeast-1）
- Python 3.10+、Ansible 2.15+、Terraform 1.6+
- Chatwork API Token・Room ID 取得済み

## クイックスタート
```bash
# 1. 環境変数をセット
export AWS_DEFAULT_REGION=ap-northeast-1
export CHATWORK_API_TOKEN="your_token"
export CHATWORK_ROOM_ID="your_room_id"

# 2. インフラをデプロイ
cd terraform
terraform init && terraform apply \
  -var="chatwork_api_token=$CHATWORK_API_TOKEN" \
  -var="chatwork_room_id=$CHATWORK_ROOM_ID"

# 3. 自己修復テスト（意図的に SG に穴を開ける）
SG_ID=$(terraform output -raw production_sg_id)
aws ec2 authorize-security-group-ingress \
  --group-id $SG_ID --protocol tcp --port 22 --cidr 0.0.0.0/0
# → Chatwork に修復完了通知が届くことを確認
```

## クリーンアップ
```bash
terraform destroy \
  -var="chatwork_api_token=$CHATWORK_API_TOKEN" \
  -var="chatwork_room_id=$CHATWORK_ROOM_ID"
```

SECTION 02

Ansible Playbook 作成

Ansible はどこで動くのか

Ansible には大きく2つの実行モードがある。このハンズオンは モード B（connection: local） を使う。

モード A — SSH して操作（一般的な使い方）

ローカルPC → SSH → 対象サーバー（nginx 設定変更など）
hosts: webservers / connection: ssh

モード B — SSH せず自分自身で実行（今回）

ローカルPC → boto3 → AWS API（SG を直接操作）
hosts: localhost / connection: local

ℹ EC2 は登場しない。 Ansible はローカルPC 上で動き、SSH も SSM も使わず直接 AWS API を叩く。自動修復の本体は Lambda。Ansible はローカルから手動確認・強制再適用するときに使う。
SG 修復 Playbook

「あるべき状態」を宣言的に記述する。ローカルPC から手動実行して状態を確認・強制適用する。

ansible/playbooks/fix_sg.yml
---
- name: Enforce Security Group Compliance
  hosts: localhost       # ローカルPC 自身で実行
  connection: local      # SSH しない。boto3 で AWS API を直接呼ぶ
  gather_facts: false

  vars:
    sg_id: "{{ sg_id }}"         # 実行時に -e "sg_id=sg-xxx" で渡す
    allowed_ssh_cidrs:
      - "10.0.0.0/8"          # 許可する CIDR（あるべき状態）

  tasks:
    - name: Get current SG rules
      amazon.aws.ec2_security_group_info:
        group_ids: ["{{ sg_id }}"]
        region: ap-northeast-1
      register: sg_info

    - name: Revoke ALL inbound rules (reset)
      amazon.aws.ec2_security_group:
        group_id: "{{ sg_id }}"
        purge_rules: true   # 現状に関わらず全ルールをリセット
        rules: []
        region: ap-northeast-1
      when: sg_info.security_groups | length > 0

    - name: Apply compliant rules only
      amazon.aws.ec2_security_group:
        group_id: "{{ sg_id }}"
        rules:
          - proto: tcp
            from_port: 22
            to_port: 22
            cidr_ip: "{{ item }}"
        region: ap-northeast-1
      loop: "{{ allowed_ssh_cidrs }}"

    - name: Notify Chatwork - Remediation Complete
      uri:
        url: "https://api.chatwork.com/v2/rooms/{{ lookup('env', 'CHATWORK_ROOM_ID') }}/messages"
        method: POST
        headers:
          X-ChatWorkToken: "{{ lookup('env', 'CHATWORK_API_TOKEN') }}"
          Content-Type: "application/x-www-form-urlencoded"
        body: "body=%E2%9C%85%20%5B%E8%87%AA%E5%B7%B1%E4%BF%AE%E5%BE%A9%E5%AE%8C%E4%BA%86%5D%0ASG%20%60{{ sg_id }}%60%20%E3%81%AE%E4%B8%8D%E6%AD%A3%E3%83%AB%E3%83%BC%E3%83%AB%E3%82%92%E8%87%AA%E5%8B%95%E5%89%8A%E9%99%A4%0A%E4%BF%AE%E5%BE%A9%3A%200.0.0.0%2F0%20%E2%86%92%20port%2022%20%E5%89%8A%E9%99%A4%E3%80%81%E5%86%85%E9%83%A8CIDR%E3%81%AE%E3%81%BF%E8%A8%B1%E5%8F%AF"
        status_code: 200
ℹ ポイント: purge_rules: true がミソ。現在の状態に関係なく「あるべき状態」を強制上書きする。これが冪等性（Idempotency）の本質。Lambda の修復ロジックも同じ考え方で実装する。
Playbook の手動実行（ローカルPC から）
terminal
SG_ID=$(cd terraform && terraform output -raw production_sg_id)

# dry-run（実際には変更しない）
ansible-playbook ansible/playbooks/fix_sg.yml \
  -e "sg_id=$SG_ID" \
  --check

# 実際に適用（強制的に正しい状態に上書き）
ansible-playbook ansible/playbooks/fix_sg.yml \
  -e "sg_id=$SG_ID"

# AWS Config Recorder の有効化
resource "aws_config_configuration_recorder" "main" {
  name     = "security-recorder"
  role_arn = aws_iam_role.config_role.arn

  recording_group {
    all_supported                 = false
    resource_types                = ["AWS::EC2::SecurityGroup"]
  }
}

# S3バケット（Config履歴保存）
resource "aws_s3_bucket" "config_bucket" {
  bucket = "config-remediation-${data.aws_caller_identity.current.account_id}"
  force_destroy = true
}

# マネージドルール: SSH を 0.0.0.0/0 に開放したら違反
resource "aws_config_config_rule" "no_unrestricted_ssh" {
  name = "no-unrestricted-ssh"

  source {
    owner             = "AWS"
    source_identifier = "INCOMING_SSH_DISABLED"
  }

  depends_on = [aws_config_configuration_recorder.main]
}

# EventBridge: 違反検知時にLambdaを起動
resource "aws_cloudwatch_event_rule" "config_violation" {
  name        = "config-sg-violation"
  description = "Trigger on Config Rule NON_COMPLIANT"

  event_pattern = jsonencode({
    source      = ["aws.config"]
    detail-type = ["Config Rules Compliance Change"]
    detail = {
      configRuleName    = ["no-unrestricted-ssh"]
      newEvaluationResult = {
        complianceType = ["NON_COMPLIANT"]
      }
    }
  })
}

resource "aws_cloudwatch_event_target" "lambda" {
  rule      = aws_cloudwatch_event_rule.config_violation.name
  target_id = "RemediationLambda"
  arn       = aws_lambda_function.remediation.arn
}
✓ INCOMING_SSH_DISABLED は AWS マネージドルール。カスタムルールを書かなくても SSH 開放を即座に検知できる。他にも RESTRICTED_INCOMING_TRAFFIC など多数存在する。
SECTION 04

Lambda 修復トリガー

Lambda ハンドラー

Config のイベントを受け取り、boto3 で SG を直接修復する。EC2 も SSM も使わない。Ansible と同じ「全リセット → 正しいルール適用」の考え方をそのまま Python で実装する。

lambda/handler.py
import boto3
import json
import os
import urllib.request
import urllib.parse
import logging

logger = logging.getLogger()
logger.setLevel(logging.INFO)

ec2 = boto3.client('ec2', region_name='ap-northeast-1')

# あるべき状態（Ansible の allowed_ssh_cidrs と合わせる）
ALLOWED_SSH_CIDRS = ["10.0.0.0/8"]

def lambda_handler(event, context):
    """AWS Config の NON_COMPLIANT イベントを受け取り SG を修復する"""
    logger.info(f"Event: {json.dumps(event)}")

    detail      = event.get('detail', {})
    resource_id = detail.get('resourceId')  # 例: sg-xxxxxxxxxxxxxxxxx
    rule_name   = detail.get('configRuleName')

    if not resource_id:
        logger.error("No resourceId in event")
        return {'statusCode': 400}

    logger.info(f"NON_COMPLIANT: {rule_name} → {resource_id}")
    remediate_sg(resource_id)
    notify_chatwork(resource_id)

    return {'statusCode': 200, 'body': json.dumps({'remediated_sg': resource_id})}


def remediate_sg(sg_id: str):
    """全リセット → 正しいルール適用（Ansible の purge_rules: true と同じ考え方）"""
    resp = ec2.describe_security_groups(GroupIds=[sg_id])
    current_rules = resp['SecurityGroups'][0]['IpPermissions']

    # 全インバウンドルールを削除（リセット）
    if current_rules:
        ec2.revoke_security_group_ingress(GroupId=sg_id, IpPermissions=current_rules)
        logger.info(f"Revoked all inbound rules from {sg_id}")

    # あるべき状態のルールを適用
    ec2.authorize_security_group_ingress(
        GroupId=sg_id,
        IpPermissions=[{
            'IpProtocol': 'tcp',
            'FromPort': 22,
            'ToPort': 22,
            'IpRanges': [{'CidrIp': cidr, 'Description': 'Internal only'}
                         for cidr in ALLOWED_SSH_CIDRS]
        }]
    )
    logger.info(f"Applied compliant rules to {sg_id}")


def notify_chatwork(sg_id: str):
    """Chatwork に修復完了を通知する"""
    token   = os.environ['CHATWORK_API_TOKEN']
    room_id = os.environ['CHATWORK_ROOM_ID']
    message = (
        f"✅ [自己修復完了]\n"
        f"SG {sg_id} の不正ルールを自動削除しました\n"
        f"修復内容: 0.0.0.0/0 → port 22 を削除、内部 CIDR のみ許可"
    )
    data = urllib.parse.urlencode({'body': message}).encode()
    req  = urllib.request.Request(
        f"https://api.chatwork.com/v2/rooms/{room_id}/messages",
        data=data,
        headers={'X-ChatWorkToken': token},
        method='POST'
    )
    with urllib.request.urlopen(req) as res:
        logger.info(f"Chatwork notified: {res.status}")

意図的に「悪い設定」を入れる

  --protocol tcp \
  --port 22 \

echo "Breach created on $SG_ID — watching for auto-remediation..."

期待される修復フロー（約10秒）
  1. [0s] SG 変更 → AWS Config が即座に検知
  2. [2s] INCOMING_SSH_DISABLED ルールが NON_COMPLIANT に変化
  3. [3s] EventBridge が Lambda を起動
  4. [8s] Lambda が boto3 で SG の全ルールをリセット → 正しいルールを適用
  5. [10s] Chatwork に修復完了通知が届く 🎉
修復確認コマンド
terminal — 修復結果を確認
# SG のルールを確認（0.0.0.0/0 が消えているはず）
aws ec2 describe-security-groups \
  --group-ids $SG_ID \
  --query "SecurityGroups[0].IpPermissions" \
  --output table

# Config ルールの準拠状態を確認
aws configservice get-compliance-details-by-config-rule \
  --config-rule-name no-unrestricted-ssh \
