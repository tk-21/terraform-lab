# ADR-001: Istio を AWS App Mesh より選択する

- **Date**: 2026-05-14
- **Status**: Accepted

## Context

EKSクラスタ上でサービスメッシュを導入する際、以下の候補を検討した：

1. **AWS App Mesh** — AWSネイティブのサービスメッシュ
2. **Istio** — CNCFプロジェクトのOSSサービスメッシュ

サービスメッシュに求める機能：
- マイクロサービス間のmTLS暗号化
- トラフィック制御（カナリアリリース、サーキットブレーカー）
- 可観測性（分散トレーシング、メトリクス収集）
- アクセスポリシーの宣言的管理

## Decision

**Istio を採用する。**

理由：

1. **ポータビリティ**: Istioは特定クラウドに依存しないため、GKEやオンプレへの移行が容易。App MeshはAWS専用であり、マルチクラウド構成やポートフォリオ汎用性に欠ける。

2. **可観測性ツールの充実**: Kiali（サービスグラフ可視化）、Jaeger（分散トレーシング）、Grafana連携がIstioのエコシステムに含まれており、観測レポート生成のゴールに直結する。

3. **OSSコミュニティ**: CNCFのGraduatedプロジェクトであり、ドキュメントや事例が豊富。ポートフォリオとして採用理由を説明しやすい。

4. **機能の成熟度**: mTLS STRICT、PeerAuthentication、AuthorizationPolicy など、セキュリティポリシーの表現力がApp Meshより高い。

## Consequences

**メリット:**
- ベンダーロックインなし
- Kialiによるサービストポロジーの可視化
- 業界標準技術としてのポートフォリオ価値

**デメリット:**
- App Meshと比較して運用複雑性が高い（istiodの管理が必要）
- メモリ消費量が増加（サイドカープロキシ = Envoyが各Podに注入される）
- EKSマネージドアドオンとして提供されないため、バージョンアップを自己管理する必要がある

**緩和策:**
- `istioctl` によるインストールをAnsible Playbookで自動化
- バージョンアップ手順を `docs/runbook/` に記載
