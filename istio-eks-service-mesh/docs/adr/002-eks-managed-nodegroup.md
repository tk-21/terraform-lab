# ADR-002: EKSマネージドノードグループを採用する

- **Date**: 2026-05-14
- **Status**: Accepted

## Context

EKSのワーカーノード管理方式として以下を検討した：

1. **セルフマネージドノード**: EC2をAutoScaling Groupで直接管理
2. **EKSマネージドノードグループ**: AWSがノードのライフサイクルを管理
3. **Fargate**: サーバーレスコンテナ実行環境

Istioのサイドカープロキシ（Envoy）はノードレベルのネットワーク設定を必要とするため、Fargateは対象外とした。

## Decision

**EKSマネージドノードグループを採用する。**

理由：

1. **AMI自動更新**: AWSがAL2023最新パッチを適用したAMIを提供し、`UpdateNodegroupVersion` APIでノードを安全にローリングアップデートできる。セキュリティパッチの適用工数を削減できる。

2. **Draining自動化**: ノード更新時の `kubectl drain` / `kubectl cordon` が自動実行され、ワークロードの安全な移行が保証される。

3. **Spotインスタンス対応**: Spotインスタンスの中断ハンドリング（2分前通知 → 自動drain）がマネージドノードグループでサポートされている。

4. **ポートフォリオ観点**: セルフマネージドは管理オーバーヘッドが大きく、ハンズオンのコアである「Istioの学習」から焦点がずれる。

## Consequences

**メリット:**
- AMIバージョン管理をAWSに委譲
- ノード更新時のPod退避が自動化
- CloudFormation Stackによるノードグループ状態の可視化

**デメリット:**
- カスタムAMI（独自バイナリやエージェント組み込み）は使用不可
- ユーザーデータスクリプトのカスタマイズに制限あり（launch templateで部分的に対応可能）
- マネージドノードグループが内部で使用するIAMロール・セキュリティグループを完全に制御できない

**緩和策:**
- OS hardening は Ansible の `os_hardening` ロールで起動後に適用
- CIS Benchmark準拠の設定はAMIではなくプロビジョニング時に実施
