# ADR-001: Terraform ベースライン設計の判断記録

**ステータス**: Accepted  
**作成日**: 2026-05-18  
**フェーズ**: Phase 1

---

## 背景

iac-trilogy-lab の Phase 1 として Terraform でインフラを実装した。
このADRは「実装しながら気づいた自分の当たり前」を言語化する記録である。

---

## 判断と理由

### 1. ファイル分割戦略: 機能別分割を選んだ

`main.tf` に全部書く「1ファイル主義」ではなく、`vpc.tf` / `ec2.tf` / `s3.tf` のように機能別に分割した。

**なぜか？**
実は深く考えずに「いつもこうしている」からだった。言語化すると：
- `terraform plan` のdiffが読みやすくなる（変更のスコープが自明になる）
- CDK/Pulumiと比較したとき、「ファイル=責務」というHCLの慣習が浮き彫りになる

**当たり前だったこと**: ファイル分割は「いつもやること」であり、なぜそうするか説明できていなかった。

---

### 2. `count` 禁止 → `for_each` を使う

今回のリソースは全て単一インスタンスなので、実際には `count` も `for_each` も不要だった。
しかし「複数化するなら `for_each`」という制約は重要な設計判断を内包している。

**なぜ `count` はダメなのか？**
`count` はインデックス（0, 1, 2...）でリソースを管理する。中間のリソースを削除すると
インデックスがずれ、全後続リソースが `destroy → create` される「デスマーチ」が発生する。
`for_each` はキー（文字列）で管理するため、この問題を回避できる。

**当たり前だったこと**: 「`for_each` のほうがいい」は知っていたが、「なぜ `count` が危険か」を
リソース再作成コストとセットで説明できていなかった。

---

### 3. `default_tags` をプロバイダーレベルで設定した

```hcl
provider "aws" {
  default_tags {
    tags = local.common_tags
  }
}
```

個別リソースに `tags = local.common_tags` を書く代わりに、プロバイダーの `default_tags` を使った。

**なぜか？**
書き忘れを防ぐため。タグ戦略は「全リソースに確実に付く」ことが前提で、
個別指定は「忘れたら終わり」のヒューマンエラーリスクがある。

**トレードオフ**: `default_tags` を使うと `terraform plan` のdiffにタグが毎回出てきてノイズになることがある。
チームで慣習が割れるため、CLAUDE.mdに明記しておく価値がある。

---

### 4. IMDSv2を強制した理由を説明できるか？

```hcl
metadata_options {
  http_tokens = "required"
}
```

「セキュリティベストプラクティスだから」で終わらせていた。

**言語化すると**: IMDSv1はHTTPリクエストだけでメタデータ（IAM認証情報含む）を取得できる。
SSRFを持つアプリケーションをEC2で動かしている場合、攻撃者がEC2の認証情報を奪取できる。
IMDSv2ではセッショントークンの事前取得が必要（PUT → GET の2ステップ）なため、
単純なSSRFでは認証情報が漏れない。

---

### 5. NAT Gateway を使わない設計

**コスト**: NAT Gateway は約 $0.045/時 + データ転送料。月32ドル以上のコスト増。
**代替**: EC2にパブリックIPを付与してIGW経由でインターネット疎通を確保。

**トレードオフ**:
- ✅ コスト：$32/月節約
- ❌ セキュリティ：EC2がパブリックIPを持つ（SSMのみ使うなら実質問題ない）
- ❌ 設計：本番パターンと異なる（本番ではNAT GW or NAT Instance を使う）

**当たり前だったこと**:「NAT GWは高い、だからVPCエンドポイント使おう」は言えても、
「なぜパブリックサブネット直でも今回は許容できるか」の理由を説明できていなかった。

---

## 自分の「当たり前」の棚卸し

| 当たり前だった行動 | 言語化した理由 | 次に気をつけること |
|---|---|---|
| ファイルを機能別に分割する | diff可読性・責務の明確化 | 分割粒度の基準を言語化する |
| for_each を使う | count のインデックスずれ問題を回避 | 単一リソースの場合は不要と判断できる |
| default_tags を使う | 書き忘れ防止 | ノイズになるトレードオフも説明できるようにする |
| IMDSv2を強制する | SSRF経由の認証情報漏洩防止 | EC2以外（ECS Task等）での対応方法も確認 |
| NAT GW を使わない | コスト最適化（$32/月節約） | 本番設計では代替案（VPCエンドポイント等）を提示する |
