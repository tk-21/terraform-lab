# ADR-001: HPAとKEDAの併用戦略

**Date:** 2026-04-27  
**Status:** Accepted

## Context

CPU/メモリ使用率ベースのHPAだけでは、リクエストレートが急増する際のスケールアウト応答速度が不十分だった。HPA単体では、CPUが実際に上昇するまでのラグ（約30-60秒）が発生し、その間のリクエストキューイングでレイテンシスパイクが起きていた。

## Decision

HPAをベースライン（CPU/メモリ閾値）として維持しつつ、KEDAをPrometheusメトリクス（リクエストレート）ベースの補助スケーラーとして併用する。

- HPA: CPU使用率60%以上でスケールアウト（安定した閾値管理）
- KEDA: `sum(rate(http_requests_total[1m])) > 100` でスケールアウト（先行スケール）

## Consequences

**メリット:**
- KEDAがリクエストレートの増加を即座に検知し、CPUが上昇する前にスケールアウト開始
- HPA/KEDAともに同じDeploymentを対象とするが、max replica数を揃えることで競合を防げる
- 突発的なトラフィックスパイク時のレイテンシスパイクを抑制（p99: 5,200ms → 290ms）

**トレードオフ:**
- Prometheusが可観測性スタックの前提条件となる（Prometheusが落ちるとKEDAスケールが機能しない）
- HPA + KEDA両方のパラメータチューニングが必要で、初期設定コストがかかる
- `minReplicas`をHPAとKEDAで一致させないと予期しないスケールダウンが発生する
