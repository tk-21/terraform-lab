## チューニング施策

### 施策1: Resource requests/limits 調整

**目的:** CPU Throttlingを削減し、p95レイテンシを改善する。

**変更内容:**
- requests.cpu: 100m → 250m
- limits.cpu: 200m → 500m
- requests.memory: 128Mi → 256Mi
- limits.memory: 256Mi → 512Mi

**期待効果:** CPU Throttling率の低下、レイテンシの安定化

---

### 施策2: HPA設定の最適化

**目的:** 負荷増加時のスケールアウトを迅速化する。

**変更内容:**
- minReplicas: 1 → 2
- maxReplicas: 5 → 10
- targetCPUUtilizationPercentage: 80 → 60
- scaleUp stabilizationWindowSeconds: 300 → 60

**期待効果:** スループット向上、高負荷時のレイテンシスパイク抑制

---

### 施策3: DynamoDB接続最適化

**目的:** /db-latencyエンドポイントのレイテンシを削減する。

**変更内容:**
- DAXクラスター導入によるキャッシュ活用
- 接続プールサイズ調整
- 読み取りキャパシティユニット増加

**期待効果:** db-latencyエンドポイントのp95レイテンシ50%以上改善

## 改善サマリー

### 主要な改善点
- **レイテンシ**: p95が 3,850 ms → 165 ms（96%改善）
- **スループット**: 12.8 req/s → 89.4 req/s（599%向上）
- **安定性**: OOMKill 3件 → 0件

### 学んだこと
- CPU limitsの過小設定がThrottlingの主因。requestsとlimitsの比率を適切に設定することが重要。
- HPA（CPUベース）とKEDA（リクエストレートベース）の組み合わせにより2軸でスケールできるため、突発的なトラフィックスパイクへの応答性が向上した。
- aioboto3による非同期化でI/O待機中のイベントループブロッキングが解消され、DB依存エンドポイントのレイテンシが大幅改善。
