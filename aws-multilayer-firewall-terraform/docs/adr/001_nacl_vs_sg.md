# ADR 001: NACL と Security Group の役割分担

## ステータス
承認済み

## コンテキスト

VPC 内のアクセス制御手段として NACL と Security Group の 2 つが存在する。
どちらも使えるが、それぞれ特性が異なるため適切に使い分ける必要がある。

本プロジェクトでは以下の 2 層のアクセス制御を設計する必要があった:
- サブネット境界での制御（Public / Private / Firewall サブネット間）
- インスタンスレベルでの細粒度制御（Web / App / DB ロール間）

## 決定

- **Security Group**: リソース（EC2 / ALB / VPC Endpoint）レベルの細粒度制御に使用
- **NACL**: サブネットレベルの粗粒度制御・明示的な拒否ルールの補完に使用

## 根拠

### Security Group を主軸にする理由

**ステートフル**であることが最大の理由。
戻りトラフィック（エフェメラルポート 1024–65535）を自動追跡するため、
インバウンドルールに 443 を許可するだけでアウトバウンドの応答も許可される。
NACL ではこれを両方向に明示的に書く必要があり、ヒューマンエラーのリスクが上がる。

**SG 間参照（Security Group ID 参照）** により、
「Web SG からの 8080 のみ App SG に許可」のように IP アドレスではなくロールで制御できる。
IP が変動する Auto Scaling 環境でも追従が不要。

**管理コスト**も低い。NACL はルール番号の順序管理が必要で、
番号が連続していると後から差し込む際に既存ルールを付け直す手間がある。

### NACL を補完的に使う理由

**明示的な DENY ルール**を書ける点が SG との最大の違い。
SG は「許可しないもの = 拒否」という暗黙の拒否しか持てない。
外部から届く前に特定の CIDR を明示的に弾きたい場合（例: 自社以外からの管理ポートへのアクセス）は NACL の DENY が有効。

**サブネット境界での多層防御**として、SG の設定ミスをフォールバックとしてカバーできる。
Firewall サブネット → Public サブネット → Private サブネットの各境界に NACL を設定することで、
単一障害点を避ける設計になる。

**ALB などの managed サービス**は SG を複数アタッチできるが、
NACL はサブネットレベルで全インスタンスを一括保護するため管理ポイントが少なくなる。

## トレードオフ

| 観点 | Security Group | NACL |
|---|---|---|
| ステート管理 | ステートフル（戻り自動許可）| ステートレス（両方向の記述が必要）|
| スコープ | インスタンス単位 | サブネット単位 |
| 明示的 DENY | 不可 | 可 |
| SG 間参照 | 可（IP 変動に強い）| 不可（CIDR のみ）|
| エフェメラルポート | 意識不要 | 1024–65535 の明示的許可が必要 |
| ルール上限 | 60 inbound + 60 outbound | 40 ルール/NACL |

## 採用した設計

```
[Internet]
    │
[NACL: public] ← HTTP(80)/HTTPS(443) ingress のみ許可
    │
[Public Subnet]
    │
[SG: amf-sg-web] ← 80/443 in, EC2 へのアクセス制御
    │
[NACL: private] ← Public Subnet からの 8080 のみ許可
    │
[Private Subnet]
    │
[SG: amf-sg-app] ← Web SG からの 8080 のみ許可
```

エフェメラルポートの扱いは NACL の Public/Private 両方のインバウンドに `1024-65535 TCP` を追加している（戻りパケットの受信許可）。アウトバウンドはプロトコル `-1`（全許可）で対応しているため、エフェメラルポートを個別に記述する必要はない。
