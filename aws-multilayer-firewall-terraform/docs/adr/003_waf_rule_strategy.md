# ADR 003: WAF ルールの優先度戦略と COUNT モードの活用

## ステータス
承認済み

## コンテキスト

ALB に WAF WebACL をアタッチする際、以下の設計判断が必要だった:

1. どのマネージドルールを使うか（コスト・WCU 上限との兼ね合い）
2. ルールの優先度順序をどう決めるか
3. 本番導入時の安全な切り替え方法

制約: 1 WebACL あたり WCU（Web ACL Capacity Unit）上限は 5000。
ただしコスト最小化のためルールは絞り込む。

## 決定

優先度の設計（小さい番号が先に評価される）:

| 優先度 | ルール名 | アクション | WCU |
|---|---|---|---|
| 10 | ブロック IP セット | BLOCK | 1 |
| 20 | AWSManagedRulesCommonRuleSet | BLOCK (`SizeRestrictions_BODY` のみ COUNT) | 700 |
| 30 | AWSManagedRulesKnownBadInputsRuleSet | BLOCK | 200 |
| 40 | レートベースルール（2000/5分） | BLOCK | 2 |
| 50 | カスタム UA ブロック（スキャナー）| BLOCK | 50 |

マネージドルール導入時は **COUNT モード**で 1 週間運用してから BLOCK に切り替える。

## 根拠

### IP セットを最優先（Priority 10）にする理由

既知の悪意ある IP からのリクエストは、ペイロードの内容にかかわらず通過させる必要がない。
最初に弾くことで後続のルール（WCU を消費する複雑なルール）の評価を省略でき、
レイテンシを下げつつコストも抑えられる。

IP セット自体の WCU は 1（最小）なので、他のルールの WCU 予算に影響しない。

### Common Rule Set (CRS) を中心に置く理由（Priority 20）

OWASP Top 10 に対応した汎用ルールとして SQLi / XSS / LFI / Path Traversal などを
一括でカバーできる。AWS が継続的にルールを更新するため、新たな CVE にも追従できる。

一方で CRS は過検知（False Positive）が発生しやすい。
特に `SizeRestrictions_BODY` や `CrossSiteScripting_BODY` は正規の API リクエストでも
引っかかることがある。そのため一部のルールは COUNT モードで様子を見てから判断する。

### Known Bad Inputs（Priority 30）の配置理由

Log4Shell (CVE-2021-44228) や Spring4Shell など、特定の既知エクスプロイトをカバーする。
CRS より後にするのは、CRS が先にブロックしたケースではこのルールの評価が省略されるため、
評価コストの節約になるから。既知の悪意あるペイロードに絞っているため過検知は少ない。

### レートベースルールの閾値（2000/5分 = 6.7 req/秒）の根拠

通常のユーザー操作では 5 分間で 2000 リクエストを送ることはない。
（ページ遷移で 20–50 req/回、高頻度でも 1–2 req/秒程度）

2000 を超えるのはスクレイピング・クレデンシャルスタッフィング・DDoS と判断できる。
ただし正規の API クライアント（バッチ処理など）がある場合はこの閾値を引き上げる必要がある。
→ 本プロジェクトはハンズオン環境のため API バッチはなく、2000 で適切と判断した。

### スキャナー UA ブロック（Priority 50）の位置づけ

sqlmap / Nikto / masscan などのスキャナーツールは特徴的な User-Agent を送る。
CRS にも UA チェックはあるが、カスタムルールで明示的に管理することで
「何をブロックしているか」を可視化し、運用時の説明責任を持てるようにした。

CRS より後にするのは、CRS がすでにブロックするケースを先に弾いてから
カスタムルールの評価に移るため（カスタムルールの WCU 消費を最小化）。

### COUNT モードの活用理由

マネージドルールを BLOCK で直接有効化すると:
- 正規ユーザーを誤ってブロックするリスクがある（誤検知）
- 本番環境であればユーザー体験の毀損につながる

COUNT モードでは、ブロック判定のログを記録するだけでトラフィックは通過させる。
CloudWatch の `CountedRequests` メトリクスを 1 週間観察し、誤検知がないことを確認してから
`override_action` を `none`（= ルールのアクション通りに動作）に切り替える。

## トレードオフ

| | マネージドルール | カスタムルール |
|---|---|---|
| 更新コスト | AWS が自動更新 | 自分でメンテナンス |
| 過検知リスク | 高め（汎用ルールのため）| 低め（意図した対象のみ）|
| WCU 消費 | 高い（CRS で 700 WCU）| 低い |
| 可視性 | ブラックボックス気味 | ルール内容が明確 |

マネージドルールは「広く浅く」カバーし、
カスタムルールは「特定の脅威を明示的に」対処するという役割分担にした。

## 今後の拡張

本番化する際には以下のルールグループの追加を検討:
- `AWSManagedRulesBotControlRuleSet`: Bot Control（追加料金あり）
- `AWSManagedRulesATPRuleSet`: アカウント乗っ取り対策（追加料金あり）
- IP レピュテーションリスト: `AWSManagedRulesAmazonIpReputationList`
