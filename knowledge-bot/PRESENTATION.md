## 1. RAGとは何か（2分）

### LLM単体だと何が困るか

```
┌─────────────────────────────────────────────────┐
│  ユーザー「先月の障害対応手順ってどうだったっけ？」        │
│                                                 │
│  LLM単体の回答：                                  │
│  「申し訳ありませんが、その情報は持っていません」           │
│                                                 │
│  理由：                                          │
│   - 学習データに社内文書は含まれていない                 │
│   - 学習データのカットオフ以降の情報も知らない             │
│   - 根拠なく回答するとハルシネーション発生               │
└─────────────────────────────────────────────────┘
```

### RAGで解決する

```
                       ┌──────────────┐
  質問                  │   ドキュメント  │
  「障害対応手順は？」 ─→  │  (S3に保存)   │
                       └──────┬───────┘
                              │ 関連チャンクを検索
                              ▼
                       ┌──────────────┐
                       │  ベクトルDB   │  ← 「意味的に近い」文書を返す
                       │ (OpenSearch) │
                       └──────┬───────┘
                              │ 関連文書 Top-K
                              ▼
  ┌────────────────────────────────────────────┐
  │  プロンプト = 質問 ＋ 検索結果（コンテキスト）    │
  └──────────────────────┬─────────────────────┘
                         │
                         ▼
                  ┌─────────────┐
                  │   Claude    │  ← 根拠ある回答を生成
                  └─────────────┘
```

### テキストをベクトルに変換するとは

```
「障害対応」  ─→  Titan Embed v2  ─→  [0.12, -0.87, 0.43, ... ]  (1024次元)
                                               ↑
「インシデント対応」も似たベクトルに変換される  ─→  [0.11, -0.84, 0.40, ... ]
                                               ↑
キーワード一致がなくても「意味が近い」ドキュメントを発見できる
```

> **[カンペ]** 「LLMは頭がいいけど、社内のことは何も知らない。RAGはその弱点を補う仕組みです」と言い切る。ベクトルの図は「単語の意味を数値の座標に変換するイメージ」と一言添えると伝わりやすい。

            │  │  └───────────────┬──────────────────────┘   │  │
            │  └──────────────────│─────────────────────────-┘  │
            └─────────────────────│─────────────────────────────┘

                                  ▼
                     ┌────────────────────────┐

                     └──────────┬─────────────┘

              ┌─────────────────┴─────────────────┐

   ┌──────────────────┐               ┌─────────────────────┐

## 3. インフラ詳細 - Terraform（4分）

### Terraform ファイル構成

```
infra/
├── eks.tf                    # EKSクラスター（t3.medium × 2AZ）
├── vpc.tf                    # VPC / サブネット
├── bedrock_kb.tf             # Knowledge Base + S3データソース + IAM
├── opensearch_serverless.tf  # AOSSコレクション + セキュリティポリシー
├── opensearch_index.tf       # ベクトルインデックス（hnsw/faiss）
├── irsa_app.tf               # Pod → Bedrock アクセス権限（IRSA）
├── endpoints.tf              # VPCエンドポイント（5種類）
├── waf.tf                    # WAFルール
├── s3_knowledge.tf           # ドキュメント用S3（KMS暗号化）
├── bedrock_guardrails.tf     # コンテンツフィルター
└── github_oidc_ci.tf         # GitHub Actions OIDC認証
```

### ポイント1：ベクトルインデックスの定義

```
テキスト                         インデックス構造
"EKSのノードグループとは..." ─→   {
                                  vector:   [0.12, -0.87, ..., 0.43]  (1024次元)
Titan Embed v2                    text:     "EKSのノードグループとは..."
で変換                             metadata: { source: "aws-guide.pdf" }
                                 }
```

```hcl
# opensearch_index.tf
resource "opensearch_index" "kb" {
  mappings = jsonencode({
    properties = {
      vector = {
        type      = "knn_vector"
        dimension = 1024        # ← Titan Embed v2 の出力次元と一致させる
        method = {
          name       = "hnsw"   # ← 近似最近傍探索（全件比較より高速）
          engine     = "faiss"  # ← Metaのベクトル検索ライブラリ
          space_type = "l2"     # ← ユークリッド距離で類似度計算
        }
      }
    }
  })
}
```

```
HNSWのイメージ：
全ベクトル(N件)を階層グラフで管理
  → 検索時は O(log N) で到達（全件スキャン不要）
  → 10万件のドキュメントでも高速に「近い」チャンクを発見
```

### ポイント2：Knowledge Base のTerraform定義

```
Terraform が設定する内容
┌──────────────────────────────────────────┐
│  aws_bedrockagent_knowledge_base         │
│                                          │
│  埋め込みモデル: Titan Embed v2           │
│  ストレージ:    AOSS                      │
│  フィールド対応:                          │
│    vector   ←→  knn_vector フィールド     │
│    text     ←→  text フィールド           │
│    metadata ←→  metadata フィールド       │
│                                          │
│  ※ フィールド名がインデックスと一致しないと  │
│     取り込みエラーになる（ハマりポイント）   │
└──────────────────────────────────────────┘
```

### ポイント3：フォールバック検索（rag_mvp.py）

```
通常フロー:  質問 → AOSS (ベクトル検索) → Bedrock → 回答
                                  ↓
             Bedrock KBが使えない場合（開発/障害時）
                                  ↓
フォールバック: 質問 → simple_retrieve() → キーワードマッチ → 回答
```

```python
# app/src/rag_mvp.py
def simple_retrieve(chunks, query, k=4):
    q = re.findall(r"\w+", query.lower())
    scored = [(sum(1 for w in q if w in c["text"].lower()), c) for c in chunks]
    scored = [(s, c) for s, c in scored if s > 0]
    scored.sort(key=lambda x: x[0], reverse=True)
    return [c for _, c in scored[:k]]
    # 質問単語の出現回数でスコアリング → 上位k件を返す
```

> **[カンペ]** Terraform詳細は駆け足でOK。「ここで大事なのはフィールド名の対応関係です。インデックスのフィールド名とKBの設定が一致しないと取り込みが失敗します」と実体験っぽく言うと聴衆の関心が上がる。HNSWは「木構造で近道を作って高速検索するアルゴリズム」程度の説明で十分。

## 4. セキュリティ設計（3分）

### アクセスキーを一切使わない設計

```
  【悪い例】アクセスキーをPodに埋め込む
  ┌────────────────────────────────────────┐
  │  Pod の環境変数                         │
  │  AWS_ACCESS_KEY_ID=AKIA...             │  ← 漏洩リスク大
  │  AWS_SECRET_ACCESS_KEY=xxxxx          │  ← ローテーション必要
  └────────────────────────────────────────┘

  【良い例】IRSA で動的に権限を取得
  ┌────────────────────────────────────────────────────────┐
  │                                                        │
  │  Pod                                                   │
  │   └── ServiceAccount: knowledgebot-sa                 │
  │            │                                          │
  │            │ OIDC トークン（一時的）                     │
  │            ▼                                          │
  │       AWS STS                                         │
  │            │ AssumeRoleWithWebIdentity                │
  │            ▼                                          │
  │       IAM Role: knowledgebot-app                      │
  │            │ 期限付き一時クレデンシャル発行               │
  │            ▼                                          │
  │  Bedrock API 呼び出し（InvokeModel / RetrieveAndGenerate）│
  │                                                        │
  └────────────────────────────────────────────────────────┘
```

### 多層防御の全体像

```
  インターネット
       │
       ▼
  ┌─────────────────────────────────────────────────┐
  │  WAF                                            │
  │  - AWSマネージドルール（SQLi / XSS ブロック）        │
  │  - レートリミット（DDoS軽減）                      │
  └───────────────────────┬─────────────────────────┘
                          │ HTTPS のみ通過
                          ▼
  ┌─────────────────────────────────────────────────┐
  │  ALB  (TLS終端)                                  │
  └───────────────────────┬─────────────────────────┘
                          │ HTTP/80 (内部)
                          ▼
  ┌─────────────────────────────────────────────────┐
  │  EKS Pod                                        │
  │  - IRSA（最小権限 IAM Role のみ）                  │
  │  - NetworkPolicy でNamespace間通信を制限           │
  └───────────────────────┬─────────────────────────┘
                          │ VPCエンドポイント（プライベート）
                          │ ※ Bedrock/ECR/S3/STS/logs
                          │   インターネットに出ない
                          ▼
  ┌─────────────────────────────────────────────────┐
  │  Bedrock / AOSS / S3                            │
  │  - S3: KMS暗号化（保存時）                        │
  │  - AOSS: 暗号化ポリシー + アクセスポリシー必須      │
  │  - Bedrock Guardrails: PIIマスキング / コンテンツ制御│
  └─────────────────────────────────────────────────┘
```

### セキュリティ対策まとめ

| レイヤー | 対策 | 目的 |
|---|---|---|
| エッジ | WAF（マネージドルール + レート制限） | Webアプリ攻撃防御 |
| 通信 | ALB TLS終端 + VPCエンドポイント | 経路の暗号化・プライベート化 |
| 認証 | IRSA + GitHub OIDC | アクセスキーレス運用 |
| データ | S3 KMS暗号化 + AOSS暗号化ポリシー | 保存データの保護 |
| アプリ | Bedrock Guardrails | PII検出・不適切出力の抑制 |

> **[カンペ]** 「この構成のポイントは、アクセスキーが一行もコードに存在しないことです」と強調する。IRSAは「KubernetesのPodにロールを着せる仕組み」と説明すると直感的に伝わる。VPCエンドポイントの話は「Bedrockへのリクエストがインターネットを経由しない、AWSの内部網だけで完結する」と言えばOK。

## 5. CI/CDとまとめ（2分）

### GitHub Actions の全体フロー

```
  開発者
    │
    │  git push (feature branch)
    ▼
  Pull Request 作成
    │
    ├──▶ terraform fmt -check     # フォーマット崩れを検出
    ├──▶ terraform validate       # 構文エラーを検出
    └──▶ terraform plan           # 差分をPRコメントに自動投稿
                                    「このPRで何が変わるか」が一目でわかる
    │
    │  レビュー & マージ
    ▼
  main ブランチへ push
    │
    └──▶ terraform apply          # 自動でAWSインフラに適用
```

### アプリのデプロイフロー

```
  app/ に変更を加えたら
        │
        ▼
  make build-push
  ┌─────────────────────────────────────────┐
  │  docker build -t knowledgebot:dev .     │
  │  docker push <account>.dkr.ecr.ap-      │
  │             northeast-1.amazonaws.com/  │
  └─────────────────────────────────────────┘
        │
        ▼
  make deploy
  ┌─────────────────────────────────────────┐
  │  kubectl apply -f k8s/base/             │  ← Namespace/SA/Ingress/HPA
  └─────────────────────────────────────────┘
        │
        ▼
  EKS が新しいイメージで Pod を入れ替え（ローリングアップデート）
```

### このプロジェクトで学べること（まとめ）

```
┌─────────────────────────────────────────────────────────┐
│                                                         │
│   RAG基礎          ─ ベクトル検索 × LLM の組み合わせ方    │
│   Bedrock活用      ─ Knowledge Base / RetrieveAndGenerate│
│   EKSセキュリティ  ─ IRSA でアクセスキーレス設計          │
│   IaC設計         ─ Terraform モジュール分割と依存管理    │
│   ゼロトラスト      ─ OIDC で全ての認証を統一              │
│   可観測性         ─ ALBログ → S3 → CloudWatch           │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

> **[カンペ]** CI/CDは「PRを出すだけでplan結果がコメントに貼られる、mergeするだけでapplyが走る」という体験を伝えるだけでOK。まとめは「一番持って帰ってほしいのはIRSAです。EKSを使うなら絶対知っておくべき仕組みなので、ぜひ試してみてください」と締める。

## 補足：手を動かす場合の手順

```bash
# 1. インフラ構築
make tf-init
make tf-apply

# 2. IRSAのARNをServiceAccountに設定
terraform output irsa_app_role_arn
# → k8s/base/serviceaccount.yaml の annotations に貼り付け

# 3. アプリのビルドとデプロイ
make build-push   # Docker → ECR
make deploy       # k8s マニフェスト適用

# 4. ドキュメントをS3にアップロードしてインデックス作成
make kb-ingest

# 5. 動作確認
kubectl get pods -n knowledgebot
kubectl logs -n knowledgebot deploy/knowledgebot
```

## Q&A

発表者：takuya

**よく来そうな質問と答え**

| 質問 | 答え |
|---|---|
| OpenSearch Serverless と通常のOpenSearchの違いは？ | サーバーレスはキャパシティ管理不要。ただしコスト最小値が高いので小規模用途には注意 |
| Bedrock Knowledge Baseを使わずに自前実装は？ | LangChain等でも作れるが、S3取り込み・チャンク分割・更新管理が自前になる |
| HNSWとFAISSの関係は？ | FAISSはライブラリ名、HNSWはその中のアルゴリズム名。AOSSはFAISSエンジン上でHNSWを使う |
| IRSAはEKS以外でも使える？ | 考え方は同じだが、EC2ならInstance Profile、ECSならTask Roleが対応する機能 |
